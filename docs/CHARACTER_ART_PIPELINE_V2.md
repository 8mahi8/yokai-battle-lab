# キャラクター制作・再制作基準 V2 — 2026-10-22

**現状：V0.1は造形・原作再現の検収に不合格。** 技術的にページが動いたことと、ジバニャンとして見えること・見て楽しいことは異なる。現行mainの`index.html`は旧検証物であり、品質基準作品ではない。新しい完成版の評価が済むまで、キャラ差し替えを本番/mainに行わない。

## 何を反省したか（V0.1の実物＋実コードの再確認）

- 目、頬、口の輪郭と位置、頭と胴体の大きさが本家の印象を再現していない。「赤い猫」で止まっている。
- 尻尾の始点・途中の形・二股の先端・霊火の構成が不適切。耳横の炎とリボン状の太い尾に見える。
- 手足・胴体のつながり、色面と影が硬く、3DSゲームらしい丸み・奥行きが弱い。
- `quarter` は独立した斜めの姿ではなく正面絵の変形。視点が変わったときに形が成立していない。
- アニメーションを先に8種類も実装し、静止画の品質、キー姿勢、動きの重心移動を後回しにした。
- `tests/smoke.cjs` はDOM・イベント・JavaScriptの破綻を検出するための**動作テスト**であって、美術品質の検査ではない。以前の「確認済み」の表現は不十分だった。
- 黒背景などのプレゼン演出に制作時間を使い、キャラクター造形の比較検討が足りなかった。効果・背景で造形の弱さを補わない。

## 品質ゲート — 順番を飛ばさない

### G0 資料・目的・権利
- 3DSの原作戦闘画面で、前衛の背面、敵の正面、必殺技の見え方を別に調べる。公式資料、実際のゲーム映像、複数の方向の画像を照合。
- 参考資料の図は公開リポジトリに転載しない。資料のURL、参照時刻、確信度（ゲーム画面/紹介図/ファンアート）だけを記録。
- 造形を新規作成しても著作権・二次的著作物の問題は消えない。公開GitHub Pagesに原作キャラを再現した素材を載せる前に権利方針を確定する。承諾・許諾未確認なら公開ビルドでは権利上独立したキャラを使い、原作比較は非公開の設計検証に留める。

### G1 造形・シルエット
- 実ゲームで見えるサイズ（目安 80 / 140 / 220 px）のシルエットを**最低3案**。色や背景に頼らず頭・耳・胴・手足・二股の尾が整っているか比較。
- 原作の特徴を観察した数値・構造メモを作る：頭身、顔のパーツ配置、目の比率、白い部分の形、鼻と口、耳、首輪／鈴、腹、手足、尻尾の分岐、火。
- 原画の顔と全身の比率が認識できるまで、リグ・動き・エフェクトを作らない。
- **この時点の成果**：白背景の無表情・無演出の原画、モノクロ縮小比較。自分で欠点を箇条書きにしてから次工程へ。

### G2 複数視点の静止画
- 正面、斜め前、横、斜め後ろ、背面で形状・大きさ・パーツの位置が矛盾しないかチェック。iPadで重要なのは背面と3/4視点。
- **正面の幅を縮めて斜め視点にするのは禁止**。必須の奥行き情報を新しく描くか、3Dから各方向をレンダリングする。
- 方式A：SVG/2Dの方向別リグを制作し、必要な部位のみ共通化。
- 方式B：**制作時だけ3Dで形状・骨格を作って方向別にレンダリング → プレイ時は軽量2Dスプライト表示**。前後視点の矛盾解消に有利。両方式を1体の静止画で比較してから決める。
- **この時点の成果**：白背景の方向別モデルシート。原作観察メモと見比べ、造形の問題を優先修正。

### G3 キーポーズ（補間なし）
- 待機（重心・呼吸）、打撃（予備動作 → 接触 → フォロースルー → 復帰）、妖術（構え → 溜め → 解放）、被弾、気絶を**まず静止ポーズで**確認。
- 背面から攻撃する際も手足・腰・頭・尾・炎の位置が自然であること。
- 接地と体重移動、前後パーツの重なり、輪郭の一貫性を目視。
- 連続再生や線形補間で静止ポーズの破綻は直らない。姿勢がおかしければG3に戻る。

### G4 アニメーション
- リグ/骨格の階層・回転中心・隠れる関節面を先に決める。顔・尾・火は独立した動きとする。
- キーポーズ間を補間。予備動作、接触、反動、復帰を区別し、すべて同速のロボット運動を避ける。
- いきなり8種類を量産しない。**待機 → 通常攻撃**の2種類を先に合格させ、残りの動きを制作する。
- 小さな画面でも、どの技を使っているか一目で分かること。

### G5 客観チェックと実機
- 1) 黒一色のシルエット 2) 白背景の原画 3) 主要ポーズのコンタクトシート 4) 連続動作動画・GIF 5) 実ゲーム画面サイズ 6) 前後・斜め全方向 を一セットにしてチェック。
- **技術ゲート**：DOM / JSエラー / パフォーマンス / タッチ操作 / ブラウザ画面はみ出し / 毎フレーム生成せずキャッシュ。
- **美術ゲート**：一見して対象の特徴が認識できるか、違和感の強い部位がないか、関節・重心が自然か、原作バトルらしい視点で成立するか。
- 技術ゲートのみ合格は**不合格**。制作AI自身が欠点を書き出して修正した上で、ユーザーに試遊を渡す。
- 実際のiPad Safariで未テストなら「未検証」と明記。合格を推測しない。

### G6 導入と公開
- ユーザー評価を得るまで **mainの既存ページは未変更**。実験は別ブランチ。
- 描画と対戦エンジンを分離し、ビジュアル改修でHP・攻撃・通信処理を変えない。
- スプライト化は必要性と性能を検証して行う。最初に少数フレーム、アンカー、方向、同じサイズの一致を確認。
- 検証結果・残課題・原画ソース・リグ・全モーション・ブラウザ試験ログをリポジトリに残す。
