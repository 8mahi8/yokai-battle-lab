# Phase44｜学校実機レビューを起点に「妖怪ウォッチ2らしい戦闘」へ戻す再設計（2026-10-27）

**状態：設計・原作比較フェーズ。これは実装完了宣言ではない。**

## 1. 変更の契機
2026-10-27、本人と友人が学校のiPad（Safari）、Google Sites上で2人対戦に成功。サークルが指で回らず、キャラの行動が見えず、攻撃ばかりのように感じ、妖気が遅いなど実機フィードバックを受け、Phase43 V3で応急対策を実施しGoogle Drive保存済み。その後、本人から**「そもそも妖怪ウォッチとしての完成度が低い」**という本質的な総評を受けた。

**今後は単なる+X%/固定秒の試遊調整より、原作の戦闘の仕組みを忠実に再現する。** 目的は原作の対人戦で成立する駆け引きが同じ理由で成立すること。見た目だけの「妖怪ウォッチ風」は目標でない。

## 2. 現在のコードにある技術資産：捨てずに分離
- `engine/phase1.mjs`: 素早さ、待ちポイント、初期待ち表などの**行動順の研究モデル**がある。研究コメントにあるように、原作全体の確定再現ではない。
- `engine/combat.mjs`: 6vs6、前後3体、性格・行動候補、ダメージ、状態、妖気、必殺、G、つつく、おはらい、固有スキルの処理が存在。**原作と同じ値・発動条件を保証しない**。ネット用の `enableLoafing` は未設定→`false`。
- `engine/selection.mjs`: 性格→行動重みはあるが、分岐・対象優先・特殊条件が一部で、数値は仮。
- `engine/soul.mjs`,`engine/playtest-soul-tuning.mjs`: 必殺ランク別容量と使用チェック、**友達用は攻撃/妖術の終了ごとに+18（仮）・非攻撃+5**。原作の「戦闘中に自然に妖気がたまる」を時間軸ごとには再現していない。
- `ui/host-auto-clock.mjs` と `lab/sites-embed-online-entry.mjs`: 実際のネット進行はホスト単独で **2600msごとに1自動行動**。原作由来の技別モーション長を意味しない。
- `ui/match-stage.mjs`: 確定スナップショットを受けるとHP/前衛状態を再描画し、最大約1.9秒の共通CSSモーションや行動バナーを表示。**技別の予備動作→命中→被弾→戻り→画面確定という独立した行動演出タイムラインを実装していない**。イベントごとの表示が似通っており、「何をしているか分からない」問題の一因。
- `engine/presentation-timeline.mjs`: 演出中の相手画面表示保留とノーモーション成立の研究モデルがあるが、`createMatchProtocol`オンライン契約に組み込んでいない。
- `network/firebase-*.mjs`: 実学校2端末で部屋接続に成功した資産。通信の全面置換は**不要**。既存公開版・main・Firebase DB/Rulesは変更しない。

## 3. 現状を「完成度が低い」と判断できる根本原因
### 問題A：戦闘時間を1個の固定タイマーで代理している
行動待ちポイントをエンジンが計算できても、ユーザーが体感する時間は「一定間隔で瞬間的にHPが変化→同種の短いアニメ」の繰り返しで、**原作の攻撃・妖術・とりつき・ガード・スキル告知・必殺ごとの演出とタイミング**を再現できていない。
### 問題B：行動の意味がプレイヤーに届いていない
誰が、どんな技を、どの対象へ、どう当てたかを最初に絵と動作で見せる必要がある。固定バナーだけでは「妖怪ウォッチの戦闘」を作り切れない。
### 問題C：原作の戦術を生む条件が有効化されていない
サボり、初期前衛補正、一部とりつき毎ターン効果、サークル演出表示保留、ノーモーションは研究または未実装。性格や妖気も暫定値中心。すべてを一度に追加せず、**実際の対戦版で働く条件**を一つずつ作る必要がある。
### 問題D：原作との差を見た目だけと誤認しやすい
原作は前衛3体が自動行動し、プレイヤーがサークル・ねらう・わざ・おはらいを操作することが核。2画面の見た目だけでは、その遊びのループを再現できない。

## 4. 再設計の優先順位

### Stage A｜「1アクションの再現仕様」を実装前に完成（最初の仕事）
資料と原作対戦動画を使って次の事実を **確定／対戦者経験／不明** で分け、技ごとの時間表と画面遷移表を作る。
- 物理攻撃・攻撃妖術・回復妖術・とりつき・ガード・サボり・必殺・スキル告知の**予備動作 / 実行 / HPや状態への反映 / 演出終了**のどこが原作映像で起きるか。
- 演出中に双方が入力できるか、入力がいつ反映されいつ相手側に見えるか。原作の**操作と相手への表示**を区別。
- 自動行動の発生時点、時間の経過に対する妖気の増加、交代後の待ちポイント。
- 原作の実測値がない箇所に「固定2.6秒が正しい」とは書かない。参考動画の該当時刻・区間で再検証できるようにする。

### Stage B｜戦闘エンジンと演出再生を分離（最優先の実装）
- ホストが戦闘の唯一の権威を維持。既存のゲームコマンドとACKは極力そのまま。
- 各自動行動の正規イベントを `actionId / actorId / actionKind / moveId / targetIds / hit / values / before/after / visualPhase` のような**実行結果**として記録する（既存イベントを段階的に拡張。互換性テスト）。
- 画面はそのイベントを **予備動作→効果発生→硬直/戻り** の順で再生。ゲストへは**同じ確定イベント**を届けるが独立でダメージ算出させない。
- 毎アクションでレンダラーが即HPを最終結果にしてしまう表示を段階化。必要時は**表示用スナップショット**と**確定したバトル状態**を分け、同期の逆転/ACK消失を防ぐ。
- 演出中でも許されるプレイヤー入力・両者の相手画面更新タイミングを独立に扱う。ノーモーションは最後にこの仕組みから自然に生じることを目指し、専用ボタンは禁止。
- Action durationは一律の「ユーザー好み」ではなく技種・仕様ごとにソース裏付けの有無を記録。

### Stage C｜6体だけで原作の自動行動が見える対戦を完成
- 6体レンタル固定・両者同一パーティは維持。原作キャラ大量追加や育成は不要。
- 性格を前後2要素（サボりやすさと行動傾向）としてデータに分離し、ガード・回復・妨害とりつき・攻撃妖術を**条件・対象・優先順**で原作に沿わせる。純確率だけではなく、ピン／残HP／バフ状態等も考慮。
- 必殺/とりつき/スキルの条件と効果を既存試遊の仮値から根拠ある原作値へ徐々に置換。
- 3体の戦闘で行動を観察→6体の対戦へ。原作不明な値は誤認防止のため別の試遊プリセットとして明記。

### Stage D｜妖気・零式・タッチの戦闘への統合
- 原作の「自然に溜まる」妖気とランク・技効果などを調査し、動いていない妖怪にも適用される条件を確認。単純な「攻撃後+18」が根本解決ではない。
- つつくは原作の隠れたツボ探し、稀な999等の出現条件を調査。0.1%は既存の仮値で**原作確率ではない**。
- 原作に近い必殺チャージ/おはらい/零式の遷移、サークルドラッグの気持ちよさを実ブラウザで見直す。

### Stage E｜厳密な対人戦仕様 / UI
- 初期前衛補正、演出中の相手前衛表示保留、サークル2回転等を資料と録画から確認し、実装フラグで順にネット対戦へ載せる。
- 上下画面の原作レイアウト、妖怪の動き/対象/攻撃方向/被弾/回復/とりつきステータス、個別技演出をレビュー。3D原作モデルの一致は現段階の必須条件ではなく、**行動の視認性と原作の因果関係**を優先。
- BGM/効果音は本人が不要としたため優先しない。

## 5. 最初の具体的な改善目標（小さく閉じる縦切り）
**「通常攻撃、妖術、ガード、とりつき、回復を、原作らしい原因と動きで画面上から区別できる6体の自動戦闘」** を先に完成。次の完了ゲートすべて必須：
1. 各行動に明確に異なるモーション（向き・移動・効果・戻り）と一致する表示がある
2. HP/状態が対応するヒット/回復フレームで変化する。1tick瞬間変化を隠すだけにしない
3. 前衛の行動頻度は `phase1` のポイントに由来し、全アクションが同一の演出長に依存しない
4. 回転・ピン・零式・おはらい・必殺・つつくが途中でも使える/使えないを原作の条件で保証
5. 1000手などの大量自動テストに加えて、実Chromium 2画面で操作・時間差スクショ・見た目レビュー
6. 旧Safari Google Sites埋め込みは次の実学校確認まで**未実測**と明記。友達と接続できたV2、改善版V3は必ず保存
7. 類似する既存研究機能を統合するときは、ネット用Contractに通せるか・ネット操作を二重処理しないか・相手側視覚が一致するかを個別確認
