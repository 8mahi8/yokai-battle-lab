## 2. 公式資料と対戦研究：根拠レベルを分ける
- **メーカー公式説明書**：[任天堂 YO-KAI WATCH 2: Fleshy Souls manual, Model Zero Command: Poke, PDFページ66（0基点65）](https://csassets.nintendo.com/noaext/image/private/t_KA_PDF/manual-3DS-Yo-Kai_Watch_2_Fleshy_Souls)。サボり・とりつき中の敵を選び、連続でつついてゲージを満たす。成功後には友達率上昇、追加のお金、**敵のSoul Meterを減らす**などの複数結果がある。妖気量・味方の受取妖怪・確率・対人専用選択率は指定していない。
- **開発元公式サイト**：[妖怪ウォッチ2 妖怪とバトル](https://www.youkai-watch.jp/yw2/game/game06.html)。「つつく」では敵のツボにより結果が異なる。**妖気の移動量は非公開**。
- **二次解説**：[通信対戦とつつく効果](https://asobigokoro.work/yokai-watch-2-ganso-honke-shinuchi/)はPvPで「ダメージ／妖気吸収／一撃999ダメージ」の3効果に絞ると説明。公式の対人結果表ではないため**未独立検証**。PvEの仲間確率やお金報酬を通信対戦へ導入しない。
- **競技者の研究**：[たくトンボ](https://note.com/tombow_yw/n/n1e4cf179d2d9)はつつくによる妖気回収の有無が対戦中の妖気速度推測を変える例を示す。また本人の行動後の妖気上昇も報告。**敵の減少=味方への同量転送、と断言できない**。妖気の自然増加とイベントが重なる場合は単純な前後差では確定できない。
- **昔のランダム対戦攻略研究**：[「妖気回復速度について」SeesaaWikiの検索索引](https://seesaawiki.jp/youkaiwatch2wifi/)は「後衛では回復速度0.75倍」「本人の行動があると2回分」の見解を検索結果に残している。しかし該当ページの文字コード混乱で原文を完全に再取得できておらず、**低信頼の追加仮説に留める**。攻撃・妖術・後衛の正規ゲージ値は本件で変更しない。
- **既存研究**：[Phase21D-Bの24条件](./PHASE21D_B_SOUL_RATE_TABLE_AUDIT_20261025.md)、[21D-B2/C1数式とつつくホストQA](./PHASE21D_BC_RATE_INTERVAL_AND_POKE_HOST_20261025.md)を再利用。そちらの「上限130の13対14ターン」は条件付きで矛盾するまま保持。

## 3. 実装・成果
### A. 診断コード
**新規**`engine/phase21d-poke-soul-trace.mjs`、純粋関数`auditPokeSoulTrace`。

- 両チーム各6体、合計12体の操作前後のSoul/上限・つついた敵・実行陣営を照合（入力欠落・ID重複・別陣営の不正対象・範囲外ゲージ・途中の上限変更は拒否）。
- 相手妖気の減少量、味方妖気の増加候補、他の敵味方妖気変化を**数値として観測のみ**提示する。
- 他の自動行動・自然回復・魂装備などの交絡を除外できない場合は`indeterminate`を返す。条件を隔離できても`target-soul-decrease-observed`は**「観測された減少」だけ**であり、「つつくの原作効果が確実に選ばれた／妖気が誰に同量移った」とは証明しない。
- 存在しない「原作の妖気吸収量」や受取人を生成しない。コンバット、ネット、レンタル構成は無変更。

**新テスト**`tests/phase21d-poke-soul-trace.test.mjs` 7件：
1. 敵減少と味方増加を観測、同量転送とは断定しない
2. 敵減少のみで味方増加がない場合に受取人を捏造しない
3. 減少なしのPokeも本家仕様を勝手に否定しない
4. 自然増加などが混在すれば判定保留
5. 逆方向の敵味方ID
6. 順序非依存・入力の非破壊
7. 12体不足・重複・不正値・陣営誤りを拒否

### B. 既存正規PvPホストの通信・操作確認
**追加**`tests/phase21d-pvp-poke-host-qa.test.mjs` 2件。
- 実際に「悪いとりつき→ウォッチ零式→つつく開始」したあと、相手がサークルを回して対象妖怪を後衛にすると、つつくがキャンセルされ、成功扱い（1対象1回）にはならない。サークルを元へ戻せば新たに開始可能。
- つつく途中でこちらのウォッチを通常へ戻すと、つつくの未完了操作を解除。再び零式にして対象が条件を満たしていれば再開始できる。
- 2ケースとも標準の`createMatchProtocol()` + `replayMatchJournal()`で検証。再試行・ルーム入力に影響する実ホストの操作状態を確認したが、**原作の全キャンセル仕様の独立証明ではない**。
