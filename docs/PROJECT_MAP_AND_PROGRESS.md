## 0. 絶対仕様（ゴールは一つ）
学校の古いiPad Safariで友達と遊ぶ、**妖怪ウォッチ2の対人戦闘ルールをまず忠実に再現した**完全無料のブラウザ1vs1。既存戦術が成立することを原作資料・実際の検証と照合した後だけ独自改善する。初期は双方同じオリジナルレンタル6体、**閃光魂なし**。本家に寄せた**上3vs3戦場／下6体メダルサークル＋4コマンド**構成。ゲームの単一HTML/CSS/JSをGoogle Sitesの「コードを埋め込む」へ**直接貼る**（GitHub Pages URLのiframeではない）。`main`・既存Googleサイト版・本番Firebaseは勝手に変更しない。完全なブラウザ再起動後の自動復元はユーザー不要の判断。

## 3. 今回した作業（Phase21D-B2＋21D-C1／2026-10-25）
**全体設計位置:** 原作戦闘仕様（Phase21D妖気）→ 既存 `engine/phase21d-soul-rate-evidence.mjs` と `engine/combat.mjs` + `engine/match-protocol.mjs` の**実際の対人ホスト**。次段のPhase22必殺連射、23オンライン安定、24学校Googleサイト単一HTMLの前提を詰める。原作と確認できない数値を通常対戦へ入れない。

**21D-B2研究＋コード:** [RC元の24件の妖気回復実験](https://note.com/ricosama0726/n/n14710bbe446c)と先行比較の唯一の食い違い（最大妖気130、隣接回復魂2つでGrade3妖気型13行動・Grade2威力型14行動）を再確認。前回の整数切り捨て仮説に依存せず、最初に満タンになるT回目と最大Cから一定の1行動回復量rを `C/T <= r < C/(T-1)` と区間化する `constantRecoveryInterval` と `compareSameCapacityRateIntervals`を追加。**rは13条件で10以上、14条件で10未満になり、両方を説明できる同一一定rは存在しない**。ただし実験条件が完全同一との証拠はなく、ROM上のグレード例外・記載誤差・ゲージ丸めなど原因は**不明**。両方の実測を維持し、数式を原作確定扱いしない。

**21D-C1研究＋実ホスト検証:** [公式零式つつく](https://www.youkai-watch.jp/yw2/game/game06.html)と[2015年の1対象1回というプレイヤー説明](https://youkai-gh.g-takumi.com/bbs_detail.php?bbs_id=29926)を再調査。既存の正規ホストコマンドだけで、実際に悪いとりつき→ウォッチ零式→つつく開始→12タップ完了→同じ対象2回目拒否→Journal再演を確認する `tests/phase21d-pvp-poke-host-qa.test.mjs`を追加。**報酬が`unresolved`で妖気移動を起こさないことは「原作では0」ではなく未検証のための安全な実装上の保留**。正規ホストが研究用妖気注入や架空の回収量を受理しないことも検証。通常ホスト・本番Firebaseへ新挙動導入なし。

**新テスト:** 21D-B2に3件、21D-C1に2件追加、[Node429/429＋研究Chromium QA](https://github.com/8mahi8/yokai-battle-lab/actions/runs/40112072068)成功。[本家風ステージChrome QA](https://github.com/8mahi8/yokai-battle-lab/actions/runs/40112072146) 成功、[Firebase Auth+RTDBローカル実2ブラウザ](https://github.com/8mahi8/yokai-battle-lab/actions/runs/40111904332) 成功（研究モジュール変更に反応して実行）。**原作3DS実機・学校iPad Safari・実Firebaseクラウド・Googleサイト直貼り未試験**。

**根拠・保留・変更範囲:** [Phase21D-B2/C1の数式・原作資料・ホストQA](./PHASE21D_BC_RATE_INTERVAL_AND_POKE_HOST_20261025.md)を参照。開発ブランチ `feat/phase1-action-circle-lab-20261023` のみ。main、学校Googleサイト版、本番Firebase・閃光魂初期OFFは変えず。君の操作はいま不要。

## 4. 次にする作業（Phase21D-B3/C2 → Phase22）
1. **21D-B3:** 攻撃・妖術時の妖気回復量のソースを確認。RC研究は非攻撃後+5を示すが攻撃は未測定。13対14の相違では技グレード以外の条件（技LV、装備LV、計測初期妖気、行動途中の効果、最大ゲージの精度）を精査。推測で既定レートを変えない。
2. **21D-C2:** 原作対人つつくの妖気回収量・受取人・標的妖気消費・対象再使用・発生確率・999ダメージが対戦でも成立するかを検証。2015年の「1対象1度」は**参考情報**で、対人全条件の確証ではない。「必殺→つつく→再必殺」は回収量の原作検証後に標準統合。
3. **21C残:** 行動順の初期権/同着は原作実機のマッチング時前衛・12体素早さ・輪の操作履歴などの資料待ち。閃光魂は初期OFF。
4. **Phase22→23→24:** 根拠が揃ったノーモーション/カウンター等→学校iPad Safariを想定したオンライン1vs1の安定化→Googleサイトへ**自己完結HTML/CSS/JSを直接コード貼り付け**。他サービス・課金・main本番を触らない。

## 5. 次フェーズへ進む条件と設計逸脱を防ぐルール
- **原作再現 → 対人戦術 → オンラインの安定 → 学校Googleサイト**の順を守る。画面装飾、独自ATB、次の5行動予測（UI標準ではOFF）、閃光魂、育成、ランキング、リプレイ、観戦は**現在のスコープに入れない**。
- 何かを「再現済み」と言うには、①資料と根拠の確信度、②戦闘コード、③再現テスト、④原作との比較ケースの4つが必要。**Node全件PASSは元ゲームとの一致を示さない**。
- 新機能の前に既存 `docs/` と `engine/` `tests/` を検索する。同じ研究を2回始めない。
- 少なくとも「原作確認済」「有力な非公式研究」「仮値」「未着手」を区別して記載。
- このファイルの **「今回」→「次」→「全体の設計のどこ」** を毎回作業終了時に更新し、GitHubとチャットの両方で報告する。大きい変更の際はここへ関連コード・run URL・次の受け入れ条件を残す。
