# Phase34｜ノーモーション必殺を「技」として作らず、原作の表示・演出仕様を先に再現する（2026-10-26）

## 最新の本人指示（優先順位を上書き）
- 本人の指摘：「ノーモーション必殺などはゲーム仕様を逆手に取る技術。**まずゲーム本体を原作に近づける**べき。相手のスキル・行動表示の間は、サークルを回しても相手側の画面にそれまでの前衛が映り、演出の終了時に変化が反映される。必殺チャージが突然完了したように見える」。
- **これを設計の最上位原則にする。ノーモーション専用ボタン、モード、スキル、即時チャージ短縮補正を作らない**。
- ネットワークを「60ターンテスト通ったから完成」とみなさないが、以後も受入CIは継続させる。通信試験だけを延々と拡張することより、原作ゲームルール・表示規則のパリティ調査を優先する。
- 原作で確認できる**分類・対象・表示条件・効果・タイミング規則は調べて採用**。不明な正確なフレーム長などは「原作未確認の仮時刻」と表示し、勝手に原作確定と呼ばない。
- 本人が「Googleサイトに貼るやつちょうだい」と明示するまで新しい単一HTMLを配布しない。学校用Phase27、実Google Sites、GitHub main、Supabase DB/RLS/Auth、他ゲームの資産は変更しない。

## 原作資料と確かめた仕組み
1. **2026年の競技者解説** [たくトンボ「妖怪ウォッチ2 知って得する対戦の基礎テクニックと仕様のだいたい全て」](https://note.com/tombow_yw/n/n1e4cf179d2d9)：「相手の画面でのサークル状態の反映が即時ではない」。とりつきモーション中の輪回転と必殺チャージは演出終了時まで相手側で見えず、チャージ完了がその間に収まれば突然必殺を撃ったように見える。**全てのモーションに適用**と記載。これは演出の表示規則であり、必殺技自体を即時チャージする効果ではない。
2. [マグロ「妖怪ウォッチ2対戦の全て」（2024）](https://note.com/uzoumzou_nanoha/n/n2fb6ae41559c)：「ノーモーション」の用途、長いとりつき・相手のおはらい・相手の必殺などの機会を記載。**サークル2回転**の例外規則も述べるが、表示を遅らせる規則と戦闘ターゲットのロック時刻は同一ではない。
3. [2023年の対戦Q&A](https://detail.chiebukuro.yahoo.co.jp/qa/question_detail/q13280480983)：終了文字表示時からチャージ開始しても遅いことがあり、実際は技/とりつきモーションの開始に合わせてチャージ。一次検証ではなくプレイヤー回答。
4. [2015年当時の手順映像](https://www.youtube.com/watch?v=6_9HFpAJEJU)、[同年の両視点比較検証映像](https://www.youtube.com/watch?v=GxCjC9STpmE)。**映像のフレーム別の両画面同期や原作の正確な長さは未測定**。本ノートは映像の存在から確定フレームを創作しない。

## 既存コード監査：どこまで既にあるか
- **研究は済んでいる**。engine/presentation-timeline.mjs の `createPresentationTimeline()` に `beginMotion()`, `record()`, `advance()` があり、演出中は輪回転/チャージ開始/完了をバッファし、終了時に初めて可視化。内部で完了した必殺チャージは `hiddenCharge:true` で `specialRelease` に変換する。**原作フレーム未確認の独立研究時計**。
- `engine/combat.mjs` は `researchPresentation:true` 時のみ上記を使用。tests/presentation-timeline.test.mjs / tests/combat-presentation.test.mjs に実チャージの出入り、見た目だけ遅延、キャンセル、輪回転の観察を実装済み。
- `engine/wheel-coalescing.mjs`, `engine/counter-window.mjs` に「2回の輪回転」「カウンター必殺」「2我慢例外」の**未確認を保持した研究モデル**がある。3回以上やロックフレーム不明を推測で確定させない。
- **現行オンライン実装には未統合**：engine/match-protocol.mjs は `researchPresentation` を通常のオンライン戦闘オプションに通さない。ui/match-stage.mjs の `makeStageView()` は毎回ホスト確定スナップショットの `frontIds` を両陣営に直ちに表示し、`latestBattleCue` と表示タイマー（通常780ms、必殺1050ms）は独立で、その表示タイマーは**「相手には輪回転・チャージが見えない時間」を制御していない**。
- したがって**ノーモーション現象は研究室の内部再現まで成功、実PvPの相手側表示ではまだ原作に近いとは言えない**。戦闘仕様の完成率やテストが多いことをもって誤認しない。

## 設計の正しい分離
**①ゲームの確定状態（ホストだけが管理）**：実際の輪の位置、妖気、入力、KO、必殺のチャージと解放、攻撃命中対象、ターン、勝敗。観客側の演出の長さ・描画遅延で勝敗を再計算しない。

**②プレイヤー本人の操作UI**：輪回転やチャージ操作は入力に従って直ちに見える（もしくは通常ACKのもとで進む）。本人の入力を「相手にまだ見えない」ために禁止/延期しない。

**③相手に見える表示UI**：確定状態の一部を演出中だけ前回の表示状態に保持。まずは**相手の前衛3体の表示・チャージ開始/進行表示**に絞り、演出終了時に新しい表示状態へ更新。チャージ開始→完了がロック区間内ならチャージ途中の演出を見せず必殺解放を見せる。**通信パケットを止めるのではなく、クライアントの表示を保留する**。HP・入力ACK・勝敗の確定はゲーム側で既に行う。

**④戦闘効果の対象ロック**：相手の見た目が古いことと、誰が技のダメージを受けるかは別の仕様。原作には2回転やカウンターの例外条件がある。研究だけで未確定の時刻・ターゲットを勝手に結び付けない。

## 開発順と検証の合格条件
1. **行動/とりつき/おはらい/必殺カットインの演出イベントと可視更新の境界を文書・モデル化**。演出の始終と「最新の戦闘状態」は区別。最初の固定時間は研究仮値と記載。
2. 研究済み `presentation-timeline` を極力再利用し、**観測する側の表示前衛3体のロックと演出終了での開放**を描画専用で実装。毎回サーバーの最新スナップショットをそのまま相手前衛に描く現在の実装を段階的に置換。
3. 片方の画面では即時に輪回転しているのに、相手側は前の3体を表示→演出終了時に最新3体を表示する**2視点の同期テスト**。バッファ中の2回転、チャージ開始→完了、キャンセル、相手が途中離脱、演出終了時の複数更新・最新Revisionとの整合を確認。
4. **演出より早くチャージが終わるとチャージモーションが相手には見えず、遅ければ進行中が見える**ことをUI/browser 2端末テストで証明。この効果がノーモーション必殺であり、専用技を追加したのではない。
5. その後にカウンター必殺・2我慢・2回転の実対象ロックの原作資料を調べ、別のターゲティング試験と整合。フレーム不明なら研究対象に残す。
6. 通常の本家に近づけるため、動作速度/チャージ所要時間/行動順など**基本ルール側の差**も順番にチェックする。学校旧iPad Safariのラグ・描画快適さを損なわないようにする。

この段階でオンライン版への新規専用『ノーモーション必殺』コマンドは**作らない**。本来のタイミングや入力・表示規則を作り、その副産物として起こることが合格条件。
